# 2026-11-15 리팩토링 전/후 성능 비교

- 전: `605ea25`(감사 보고서만 더한 `ab2ba29`와 코드가 같다). 후: `refactor/perf-lean-audit` HEAD.
- 근거 감사: [2026-11-15 성능·군더더기·가독성 감사](../audits/2026-11-15-performance-lean-audit.md).
- 장비: Apple Silicon Mac 1대, Python 3.13 venv(`backends/.venv`), Node(프론트 `node_modules` 공유).
- 방법: 유료 API·외부 DB 없이 같은 벤치 스크립트를 두 체크아웃에서 돌렸다. LLM·법령 러너·HTTP 응답은 고정 지연을 둔 가짜다. 그래서 **호출 수와 크기는 정확한 값이고, 시간은 가짜 지연을 가정한 상대 비교**다. 실제 Claude·DART·Tavily 지연과 비용은 재지 않았다.
- 시간 측정은 다른 작업이 CPU를 쓰지 않을 때 전·후를 번갈아 한 번씩 돌렸다. 시나리오 안에서 3회 반복한 것은 중앙값이다.
- 벤치 스크립트는 일회성이라 저장소에 넣지 않았다. 회귀는 각 수정 커밋의 테스트가 지킨다(감사 문서 상태 줄).

## 시나리오 설명

- S1 리포트 조립: 고정 입력(`tests/test_report_v2._inputs`)으로 `nodes.assemble`을 부르며 5ms 간격 타이머의 최대 지연을 잰다. 실제 폰트 서브셋을 포함한다.
- S2 규제 검토: 금융업·리스크 기사·제재 공시가 모두 있는 상태로 `regulatory_check`를 부른다. LLM 0.5초, 법령 러너 1.0초.
- S3 체크포인터: `/chat` 핸들러를 실제 `AsyncSqliteSaver`로 2턴 돌린다. 라우터·검증은 가짜, 법령 러너는 3단계 하위 그래프.
- S4 원문 재무제표 1건: 재무제표 절(표 4개+주석 표 400개)과 본문 약 4.8MB인 합성 문서를 `original.statements`로 읽는다.
- S5 원문 분기 8개: S4 문서를 응답 0.3초, 동시 4개 가짜 DART로 `history.from_original`에 넣는다.
- S6 검증: 투자 권유 단어가 든 주장 1개로 `verifier.verify`. LLM 0.5초.
- S7 기업 검색: 합성 115,000행 기업 목록으로 `corp.search_keyword` 10번.
- S8 임베딩: 500개씩 2번 `embed`(64개씩 배치, 응답 100ms).
- S9 뉴스: 같은 기업으로 `run_pipeline`을 동시에 2번(질의 계획 0.5초, 검색 0.2초).
- S10 리랭커: 새 프로세스에서 첫 `rerank`(20건). 전은 예열이 없어 첫 질문이 모델 로딩을 기다린다. 후는 lifespan의 `warmup()`이 끝난 뒤의 첫 질문이다.

## 한계

- 실제 외부 API 지연·비용, 브라우저 렌더링, 다중 사용자 부하는 재지 않았다.
- S1·S4의 시간은 이 Mac의 CPU 기준이다. 수정의 효과는 "같은 일을 루프 밖에서 한다"는 것이라 벽시계 시간은 거의 같고, 루프 정지 시간이 준다.
- 리랭커 예열은 법령 DB(Weaviate·Neo4j)가 연결될 때만 돈다. 예열 중에 온 첫 질문은 남은 시간만큼 기다린다.
- 프론트의 타자 효과 제거(답마다 setMessages 150~212회 → 1회, 표시 지연 2.4~3.4초 → 0)는 옛 코드의 간격·글자 수로 계산한 값이고 브라우저에서 재지 않았다.
